## 1. Exact mechanics

The list is **YAML-driven, not hand-edited README**. Contributors never touch `README.md` — it's generated.

- **Where to add:** one new YAML file under `data/{category}/`, filename kebab-case. Categories seen in `data/`: `agents/`, `plugins/`, `projects/`, `resources/`, `themes/` (`examples/` also exists as a top-level dir but is not a submission category).
  - Professor fits **`data/projects/`** — it's a cross-runtime framework/tool, not an OpenCode plugin, theme, or agent-only package.
- **Schema** (`data/schema.json`, draft-07): required fields `name`, `repo` (URL), `tagline` (string, **max 120 chars**), `description`. Optional: `scope` (array, enum `global`/`project`, defaults to `[global]`), `tags` (array of strings), `min_version` (semver pattern), `homepage` (URL), `installation` (markdown string). `additionalProperties: true`, so extra fields don't hard-fail schema validation, but only the documented ones are meaningful.
- **Ordering:** files within `data/projects/` are plain filesystem entries (currently ~65 files, e.g. `agent-dotfiles.yaml` … `vibe-kanban.yaml`); the generator presumably sorts alphabetically for the README (existing filenames run roughly A→Z). No manual README edit needed or wanted.
- **Generation script:** `scripts/generate-readme.js` (invoked in CI), regenerates `README.md` and `dist/registry.json` (via `scripts/export-json.js --pretty --output dist/registry.json`) from all `data/**/*.yaml`. **Contributors do not run or commit this** — `.github/workflows/generate-readme.yml` runs it automatically on every push to `main` that touches `data/**`, commits `README.md` + `dist/registry.json` as `github-actions[bot]`, and pushes back to `main` (with retry-on-race logic, up to 5 attempts). So a merged PR that only adds the YAML file is correct; the bot's own follow-up commit does the README diff.
- **CI on the PR itself:** `.github/workflows/validate-pr.yml` triggers on `pull_request` when `data/**` paths change; it runs `node scripts/validate.js <changed-yaml-files>` (via `tj-actions/changed-files`) against `data/schema.json`. This is the only gate a submission PR must pass before a maintainer looks at it.
- **PR template** (`.github/PULL_REQUEST_TEMPLATE.md`): checkboxes for submission type (Plugin/Project/Theme/Agent/Resource), Name/Repository/Tagline fields, and a requirements checklist (relevant, public, actively maintained, not a duplicate, correct folder, kebab-case filename).
- **contributing.md** entry requirements: Relevant to OpenCode, Public, **Maintained — active commits within the last 6 months**, Unique, Complete (all required fields). No explicit star minimum documented anywhere in contributing.md, schema, or PR template.
- Suggested commit-message convention from contributing.md: `docs: add my-plugin to plugins` (the observed real-world PR title convention: `docs: add <name> to <category>`, e.g. `docs: add axi-memory to projects`).

## 5. Risks

- **Staleness:** no PR has been merged in this repo since 2026-07-03 (~10 weeks as of 2026-09-14); zero commits of any kind (not even bot README-regen commits) since that date; 40+ open PRs are unaddressed. A correctly-formed, schema-valid PR is very likely to sit indefinitely rather than merge on any predictable timeline. This is the dominant risk, independent of submission quality.
- **Scope fit:** `data/projects/` is the right category (Professor is a broader cross-runtime framework, not an OpenCode-only plugin/theme/agent-pack), consistent with how similar multi-purpose entries (e.g. Vestige, eval-harness, opentab) were categorized as "projects."
- **Repo URL discrepancy:** this task's candidate URL is `https://github.com/mreza0100/professor`; an earlier draft in this repo's `docs/demo/awesome-list-entries.md` §7 used `https://github.com/rezzminator/professor` for the same project and proposed a `<details>`/badge-style entry — that draft predates discovery that the list is YAML-driven (no hand-written `<details>` block is ever committed; the generator produces the README). This file supersedes that entry's format for this specific list; the org/user portion of the URL should be confirmed against the actual live repo before any real submission.
- **"Maintained" criterion:** contributing.md requires "active commits within the last 6 months" of the *submitted project* (Professor qualifies — daily activity) — not of the awesome-list itself, so this is a pass condition for us, not a blocker, though it doesn't offset the list's own staleness above.
