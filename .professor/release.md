# Release — framework changes pending publication

`releases/vX.Y.Z.md`, then clears this file, keeping this header.

Shape: `- {Tier}: {scope} — {semantic change}`, plus a `#### → For:` line when adopters must act,
and `(cost)` on any env / hook / permission / model-config delta.

## Pending

- Minor: `templates/themes/` + `pfm install` — three bundled Claude Code overlays, one per fleet account medal (`professor-gold` 🥇, `professor-silver` 🥈, `professor-bronze` 🥉): Tokyo Night with a per-account input bar (`promptBorder` + `promptBorderShimmer`), merged onto the fetched base at install so the base is never vendored; `sources.json` gains a `bundled` section (optional `base` naming a `source_fetched` theme) the installer reads from the source clone or downloads from beside the release manifest, under the same ownership ledger; a missing or non-JSON bundled file, an unreachable base, or a `base` that is not `source_fetched` is a named skip or refusal, never an absence.
- Fixed: `templates/themes/README.md` claimed pfm embeds palettes at build time (nothing did) and a vendored `tokyo-night.json` contradicted the manifest's never-vendor rule — the copy is gone, the README describes the two manifest kinds as the installer implements them.
#### → For: run `pfm install --yes` to place the palettes; set `"theme": "custom:professor-{gold|silver|bronze}"` per account `settings.json` (or `/theme`) to pick one.
- Fixed: `templates/project/codex/README.md` + `codex/skills/wave-builder/SKILL.md` — the two rows and the launch line that forbid Codex's full-access sandbox and never-ask approval as repo defaults no longer spell the literal config values; plugin scanners regex-match those tokens in any markdown and dock the adopter for prose that bans them.
- Fixed: pfm — `pfm install` no longer aborts when the pre-split `config.json.pre-split` it wants to park already exists with identical bytes; a differing backup is still refused, and the refusal now says the two files differ.
- Minor: pfm — `pfm doctor` exits 3 when a state the installer owns is missing or broken (required dependency, launcher, hooks, host overlays, global agents, config or database health) and 1 when only advisory rows warn; `pfm update` now gates on failures alone, runs a baseline doctor before the install, and after it prints `doctor after update: warnings=N (before update: M)` plus every warning row the update introduced. A host with standing warnings the update cannot influence is no longer un-updatable; a rollback's doctor warnings are reported, never claimed as residue.
#### → For: hosts still on v0.77.x — the installed `pfm update` still rolls back on any doctor warning; if yours does, update by hand once: `git -C "$HOME/.professor" fetch --tags && git -C "$HOME/.professor" merge --ff-only vX.Y.Z && make -C "$HOME/.professor/pfm" host-install && pfm install --yes`.
- Fixed: pfm — `pfm update` hands the post-install doctor the config file the update just migrated (`config.json` → `pfm.config.json`) instead of the old name, so the gate judges the host's real accounts, MCP servers and spawn policy rather than defaults; a rollback restores the config files the migration renamed before it reruns the previous installer, so the restored release reads its own config and no longer disables the MCP launch agent it finds "unconfigured".
- Fixed: pfm — `pfm install --yes --config <path>` refuses to run when that path does not exist (converging on defaults would boot out and delete every MCP service the missing file enabled); the preview names the skip. A launch-agent or unit removal now says which config it read the disabled state from.
#### → For: anyone whose rollback lost `com.professor.pfm.mcp.plist` — `pfm install --yes` on the current release re-creates and bootstraps it; the timestamped `.pre-professor-<ts>` copies beside it can be deleted afterwards.
- Fixed: pfm — a hook of pfm's own shape naming a subcommand this pfm does not implement (what a rolled-back update from a newer release leaves behind) is now reported by `pfm doctor` as `stale` and removed by `pfm install --yes`; a rollback that has to leave a hook file untouched (something rewrote it mid-update) names the stranded entries it carries.
#### → For: hosts on v0.76.0 or older whose `pfm update` rolled back — the restored pfm exits 2 on the newer `exit-close`/`exit-intercept` hooks, which erases every prompt in a NEW chat. Before starting a chat, remove the two entries whose command ends in `pfm internal exit-close` (SessionEnd) and `pfm internal exit-intercept` (UserPromptSubmit) from each account's `settings.json` (`~/.claude/settings.json`, or `~/.cc/<n>/settings.json` per account), then retry the update; the current release's `pfm install --yes` removes such entries itself.
- Fixed: pfm — MCP client registration and the `doctor: mcp client=claude` row now cover every user-scope `.claude.json` a pfm-launched Claude can read: `~/.claude.json` for the account pfm spawns without `CLAUDE_CONFIG_DIR`, `<dir>/.claude.json` for every explicit account, and `$CLAUDE_CONFIG_DIR/.claude.json` when the shell exports that variable (the `claude` launcher passes it through). Each row and install line names which file it is and why; a host whose shell set `CLAUDE_CONFIG_DIR` had pfm's `chat` and `harvester` tools registered in a file Claude never opened.
#### → For: hosts that export `CLAUDE_CONFIG_DIR` — run `pfm install --yes` once; a hand-made `claude mcp add` for `chat`/`harvester` can then be removed (`claude mcp remove <name>`), pfm owns both.
- Fixed: pfm — the `harness-prompt` doctor check captures Claude Code's system prompt from a throwaway `CLAUDE_CONFIG_DIR`, so a subscription (OAuth) login no longer routes the probe past pfm's local sink; when a CLI still answers from the real endpoint the row says `CANNOT CAPTURE … OAuth-only routing` instead of timing out, and `pfm doctor --verbose` keeps the run's stdout/stderr under `tmp/pfm-doctor/`. Baselines unchanged.
- Minor: pfm — pfm owns Claude Code version retention, since its `claude` launcher disables the native installer's cleanup: `pfm doctor` gains `claude-versions` (count, bytes, newest, versions with live processes, prunable size), `pfm install` previews and applies a prune that keeps the two newest builds, any build a live process is executing, the configured `claude.binary` and a displaced native target — and refuses, naming each, whatever it cannot prove unused (a failed process probe prunes nothing). The launcher now picks the highest version, not the freshest file, and does so in Go (`pfm internal claude-version`).
#### → For: hosts with `~/.local/share/claude/versions/` older than two releases — run `pfm install` to see the prune plan, then `pfm install --yes`.
- Fixed: pfm — `pfm install --vscode` registers the Professor extension in each VS Code product's own `extensions/extensions.json` and verifies the entry, instead of only linking the folder: modern VS Code loads user extensions from that index, so a product whose index predated the link (Insiders on the reporter's host) never loaded it while the install reported success. Uninstall removes exactly that entry. `pfm doctor` gains one `vscode` row per product (link, index registration, version) and per owned settings file (profile, default). The `PFM` default terminal profile now carries an icon and colour (`mortar-board`, magenta); an operator's own edit still wins.
#### → For: VS Code users — run `pfm install --yes --vscode`, then **Developer: Reload Window**; you will see `Professor` in the Extensions view and a **Professor** entry in the terminal `+` dropdown (each new one takes the next icon and colour). The default `+` terminal stays the `PFM` profile, one icon, opening the fleet picker. The `Professor: New Chat Terminal` command and its `Ctrl+Shift+Alt+T` / `Cmd+Shift+Alt+T` chord open the same terminal as the dropdown entry.
- Fixed: pfm — the Professor VS Code extension's `Professor: New Chat Terminal` command creates its terminal through the extension's own contributed profile, the same route as the **Professor** dropdown entry, so a terminal opened from the command or its keybinding carries the cycling icon and colour instead of the default profile's; the extension contributes a default keybinding (`Ctrl+Shift+Alt+T`, macOS `Cmd+Shift+Alt+T`) for it. `workbench.action.terminal.newWithProfile` cannot address a contributed profile by name — VS Code resolves that argument against settings profiles only — so binding the profile directly stays impossible.
